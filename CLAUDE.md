## Development Commands

### Frontend Development
- `VITE_API_BASE_URL=http://localhost:5000 npm run dev` - Vite dev server on http://localhost:5173 (PowerShell: `$env:VITE_API_BASE_URL = 'http://localhost:5000'; npm run dev`). Without the variable the page calls relative `/api`, which Vite does not proxy
- `VITE_API_BASE_URL=https://gbacpod.com npm run build:prod` - the production build CI and Netlify run (`NODE_ENV=production vite build`, POSIX syntax; on Windows use `npx vite build`, production is Vite's default mode). A production build refuses a missing or non-`https://` `VITE_API_BASE_URL`
- `npm run build` - `vite build` without the `NODE_ENV` prefix; `npm run preview` serves `dist/`
- `npm run lint` - Run ESLint on JS/JSX/CJS files (errors fail the gate, warnings are informational; 3 `exhaustive-deps` warnings are expected, in `App.jsx` and `DashboardView.jsx`, D3; the other four went with the components Phase 4 deleted)
- `npm run security:audit` / `npm run security:audit-fix` - `npm audit` / non-breaking `npm audit fix`; never `--force` (the two remaining advisories, Vite and esbuild, are dev-only and need Vite 8; `npm audit --omit=dev` reports none; `deploy/README.md` section 12)

### Backend Development
- `npm start` or `node server.cjs` - Start Express.js backend server on port 5000
- Backend runs on http://localhost:5000 with CORS enabled for development
- `npm run create:admin -- <username> <password>` - add a partner (`create-admin.cjs`; refuses an existing username)
- `npm run reset:password -- <username> <newPassword>` - reset a forgotten password (`scripts/reset-password.cjs`); prints `Updated 1 user`, or `No such user` and exits 1. On Render, run it from the web service's Shell tab, which has the service's environment; locally, set `DATABASE_URL` to the Render database's External Database URL and `DATABASE_SSL=no-verify`. Both scripts validate with `utils/passwordPolicy.cjs` and connect through `db.cjs`
- `npm run check:schema` - read-only: lists every foreign key to `users` with its `ON DELETE` action and the clients per creating account; ends `OK: ...` and exits 0, or `FAIL: ...` and exits 1 when any key cascades (`scripts/check-schema.cjs`)
- `npm run delete:user -- <username>` - delete an account without touching the book (`scripts/delete-user.cjs`): one transaction that refuses while any key to `users` cascades, refuses the last account, and commits only if the client and revenue-row counts are unchanged. Runbook `deploy/README.md` 7.3. Both run where the two scripts above do and share the check in `utils/schemaCheck.cjs`
- `npm run reset:book`, then `npm run reset:book -- --confirm` - start the book over (`scripts/reset-book.cjs`; people plan P7, runbook `deploy/README.md` 7.4). Without an argument it prints each foreign key to `clients` and the numbers of accounts, people, clients, revenue rows and the rows of any other table that references `clients`, deletes nothing and exits 1; any other argument is a usage error that needs no database. With `--confirm`: one REPEATABLE READ transaction that locks `clients` against writes (10 s lock timeout), refuses while any foreign key to `clients` is not `ON DELETE CASCADE` (`checkClientForeignKeys`), deletes every client, and commits only if `clients`, `client_revenues` and every other referencing table (production may still hold V2's `revenues`) are empty and the account and people counts unchanged (`checkBookReset`); prints `Removed <n> clients and <r> revenue rows. Accounts: <a> and people: <p>, unchanged.` Accounts and people are never touched. Runs where the scripts above do; there is deliberately no API endpoint or button for it
- `npm run unescape:book`, then `npm run unescape:book -- --confirm <n>` - repair the client text the request sanitizer stored HTML-escaped before Tier 2 WP5 (`scripts/unescape-book.cjs`, pure half `utils/unescapeBook.cjs`; runbook `deploy/README.md` 7.5; once, between WP5's two PRs, on the API that lists `plain-text` in `/api/health`). Without an argument it lists, for `clients.name`, `notes`, `primary_lobbyist`, `client_originator` and `lobbyist_team` (element by element), the clients whose text `unescapeStored` would change, with a few as stored and as repaired (a note's text is never printed, only its length), the number of clients to repair, the names two or more clients share regardless of case (the import's rule), entity-like text the repair leaves as it is and any other text column of any table holding entity-like text (never changed), ends with the exact `--confirm` command, changes nothing and exits 1; any other argument is a usage error that needs no database. With `--confirm <n>`: one REPEATABLE READ transaction that locks `clients` against writes (10 s lock timeout), refuses unless exactly `<n>` clients hold escaped text or while any name is shared regardless of case, writes `unescapeStored` of each of those columns by id (as text), and commits only if nothing is left to repair and the rows read back are what it wrote; `updated_at` is left as it is. Prints each client it changed and exits 0; a second run finds nothing (`--confirm 0` commits nothing). Runs where the scripts above do; there is no API endpoint for it, and never in `init-db.sql`

## Architecture Overview

This is a **Client Portfolio Optimization Dashboard** for government relations attorneys, consisting of:

### Frontend (React + Vite)
- **Framework**: React 18 with Vite bundler
- **State Management**: Zustand (`src/portfolioStore.js`); clients come from the API, and only UI state is persisted to localStorage
- **UI Library**: Shadcn/UI components with Tailwind CSS
- **Charts**: Recharts for data visualizations
- **Main Entry**: `src/main.jsx` renders `src/App.jsx`

### Backend (Node.js + Express)
- **Server**: Express.js server in `server.cjs` (`PORT`, default 5000; Render sets its own). API only: the page is served by Netlify, and Express serves no static files
- **API Routes**:
  - `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`, `POST /api/auth/change-password` (`routes/auth.cjs`)
  - `GET /api/data/clients`, `POST /api/data/clients`, `PUT /api/data/clients/:id`, `DELETE /api/data/clients/:id`, `POST /api/data/process-csv` (`data.cjs`; the year rule and the import sheet, below). `POST` and `PUT /api/data/clients` check the fields with `checkClient` (`utils/clientRules.cjs`, Tier 2 WP4, S7) and then the people (`validateAssignment`), and answer one 400 `{ success: false, error: 'Validation failed', details: [{ field, message }] }` with both lists' details, the fields' first in the body's order, writing nothing; a body that is not an object answers only `{ field: 'body' }`, and a refused `PUT` answers 400 before the client is looked up. The rules: a name required, at most 255 characters and in the form's pattern, checked as it arrives (trimmed, and since Tier 2 WP5 not escaped), which is what `clients.name` (`VARCHAR(255)`) stores, so a name holding an entity (`Barnes &amp; Noble`, as a client saved before WP5 is stored until the repair) is refused as the form refuses its `;`; until WP5 the name was read through `unescapeStored` and a second rule refused one over 255 characters once escaped; practice areas a list from the twelve; conflict risk `Low`, `Medium` or `High`; cadence one of the five; stickiness 1 to 5; `high_maintenance` a boolean; revenue a list of `{ year, revenue_amount }`, each year a whole number the import reads as a `YYYY Contracts` column (1900 to 2099) and given once, each amount a number from 0 to 1,000,000,000 (the form's limit); every value exactly as the form sends it (no case folding, no numbers as text). Blank is allowed where the book holds one, as the import writes it: no practice areas, no cadence, not rated; name and conflict risk are required. A field left out takes the route's default, as before (`NULL` for practice areas and cadence, not rated, `high_maintenance` false, no revenue on `POST`), and a `PUT` without `revenues` leaves the stored revenue as it is (`revenues: []` clears it; until WP4 it deleted every row). A revenue detail's `field` is `revenue_<n>` for the n-th entry, counted from 0: the client form's key for its row. Notes, `originator_is_firm` and unknown fields are not checked. `PUT /api/data/clients/:id/second-chair` `{ second_chair_id, expected_second_chair_id }` (Phase 6, P9) sets one client's second chair and its legacy `lobbyist_team` and nothing else (logged as `second-chair` from Tier 2 WP6; a request for the seat the client already holds writes nothing): the client is read `FOR UPDATE` (by `id::text`), the person `FOR SHARE` and checked by `validateAssignment`; 409 when the stored seat is not `expected_second_chair_id` (null for none) or the client has no lead, 400 with `details` for the lead, an inactive or unknown person. `PUT` and `DELETE /api/data/clients/:id` also compare the id as text, so an id of the other table shape's type or a malformed one answers 404 `Client not found` (Tier 2 WP2); every client write takes its pool connection with `await` and guards the `ROLLBACK` in its `catch`. A person id above PostgreSQL's `integer` range matches nobody (`parseId`, `utils/people.cjs`): 400 `Validation failed` on the client writes, 404 on `PUT /api/people/:id`. The import's request-check 400 (`CSV validation failed`) gives each detail as `{ field, message, value }`. `POST /update-client`, `/optimize-portfolio` and `/analytics`, which nothing called and whose `update-client` scored with a second, retired formula, were deleted in Tier 2 WP2 (S3) and answer 404. **Who changed what, and edit conflicts** (Tier 2 WP6, S9, S10): every client write reads the client it changes `FOR UPDATE`, writes, reads what it wrote, and inserts one `client_changes` row per client whose fields or revenue changed (`utils/clientChanges.cjs`), in the write's own transaction: a failed insert fails the write (500, rethrown without PostgreSQL's `detail`, which would print the row and its note), so a change never lands without its row; a write that changes nothing is rolled back (no row, no `updated_at`). Sources: `form` (`POST`, `PUT`), `delete`, `second-chair`, `import`. `clients.updated_by` is set with `updated_at`; it and `changed_by` are written as `(SELECT id FROM users WHERE id = $n)` with the username copied, so a session whose account is gone saves with both null. Every client response carries `updated_by` (`c.*`) and `updated_at_exact`, `to_char(updated_at, 'YYYY-MM-DD"T"HH24:MI:SS.US')`: pg reads the `TIMESTAMP` column into a JS Date with milliseconds only, in the process's zone, so a Date never matches what is stored. `PUT` takes `expected_updated_at`, that text or null (a client whose `updated_at` is NULL): absent is no check (the older page, a direct request, still logged); anything else is a 400 detail `{ field: 'expected_updated_at' }` with the fields' and people's. The order: the body's 400 (the fields, the token's form, the people) before the client is looked up, then 404, then 409 `{ success: false, error, latest_change }`, `latest_change` `{ changed_by_username, source, created_at }` from the client's newest history row or null, `error` naming who and when in America/New_York; nothing written. `DELETE` takes no token (the plan gives it none) and logs every field the client had, and its revenue, to null, with its name. `GET /api/data/clients/:id/changes` answers `{ success, changes: [{ id, client_id, client_name, changed_by_username, source, changes, created_at }] }` newest first (`created_at`, then `id`), from `client_changes` alone by the id as text: a deleted client's history answers as any other, and an id with none answers `[]`. The import writes and logs only the clients the file changes or creates (below)
  - `GET /api/ai/book` - the book as the AI sees it (`routes/ai.cjs`, Tier 1 WP2): `{ success, reportingYear, clientCount, peopleCount, chars, estimatedTokens, text }`, built at each request by `loadBook` (`models/bookModel.cjs`, shared with the transition plan) with `buildBook` (`utils/book.cjs`) from `clientModel.listWithMetrics()` and `SELECT id, name, role, active FROM people`. `peopleCount` is the people the text lists; `estimatedTokens` is `chars / 4`, rounded, an estimate (no Anthropic call, no token count).   - `POST /api/ai/ask` `{ question }` and `POST /api/ai/brief` `{}` - Ask the book and the brief, the AI tab (`routes/ai.cjs`, Tier 1 WP3): behind `authenticateToken` and the two AI rate limiters, no request pass (the question is trimmed and otherwise sent as written). `checkQuestion` answers 400 for anything but 1 to 2,000 characters; an empty book answers 400 `The book has no clients yet.`; then one `complete()` call with the shared system blocks (`systemBlocks`, `utils/askPrompts.cjs`) and `maxTokens` 32,000, answering `{ success, id, saved, kind, question, answer, truncated, refused, refusalCategory, servedBy, model, usage, costUsd, reportingYear, timestamp }` (`model` is the one requested, as in the `ai_call` line; `question` null for the brief); errors through `describeError`, and never saved. A failure after the stream opened is `event: error` `{ error }` with `describeError`'s message, logged and not saved. When the page's connection closes, the route stops writing and lets the call finish and save (T15), with one `ai_stream_closed` log line (`label`, `userId`, `opened`). The limiters count a streamed answer once (T16). Each `data` is one line of JSON (`sseEvent`)
  - `GET /api/ai/answers?before=<id>&limit=20`, `GET /api/ai/answers/summary` and `GET /api/ai/answers/:id` - the saved answers (`routes/ai.cjs`, Tier 1 WP4; `models/aiAnswerModel.cjs`, SQL in `utils/aiAnswers.cjs`), every partner's, behind `authenticateToken` with no AI rate limiter. **CSV year rule (D5).** No revenue year is hard-coded anywhere. A CSV's revenue
columns are its `YYYY Contracts` headers (case-insensitive), and the file is
authoritative for exactly those years: an amount > 0 upserts the
`(client, year)` row, a blank or `$0` cell deletes it, and years the file does
not mention are left untouched. A 2026-only sheet therefore updates 2026 and
keeps 2023–2025; a corrected sheet can still zero out a year. A file with no
year columns writes no revenue and returns the validation warning
``No `YYYY Contracts` columns found; revenue not changed.``
The import deletes every `(client, year)` pair the file names and inserts the
positive amounts, as the client form writes revenue; it uses no `ON CONFLICT`
and no type cast on `client_id` (production's older tables, under File
Structure). `processCSVData` attaches the file's years to every client as `revenueYears`,
and `POST /api/data/process-csv` returns them as `summary.revenueYears`.

**Import sheet (P8; `docs/plans/people-and-second-chair.md` section 3).** Beside
`CLIENT` and the years, the only structural columns, a CSV may carry `Lead`,
`Second Chair`, `Originator`, `Credit To Firm`, `Stickiness`, `Cadence`,
`Handful`, `Conflict Risk`, `Practice Area` and `Notes`, matched
case-insensitively and trimmed (`CLIENT` still matches exactly). A
`Contract Period` column is ignored like any unknown header (P13): a sheet that
has it imports exactly as one without it. As with the years, the file is authoritative for exactly the columns
it has. A column it lacks leaves that field as it is: the columns the import has
always written keep their preserve logic, and `stickiness`, `high_maintenance`
and the four people columns are left out of the `UPDATE` (`importWriteColumns`),
so a file without the new columns writes what it wrote before. A blank cell in a
column the file has clears the field: no second chair, no originator,
stickiness NULL, Handful false, Conflict Risk `Medium`, practice areas `{}`,
notes and cadence `''`. Names resolve against the People list regardless of case,
as the sheet spells them: since Tier 2 WP5 every cell is stored as typed,
trimmed, and neither escaped nor decoded (until then the request sanitizer
escaped each cell and `decodeHTMLEntities` decoded it again, which also

length escaped). A `CLIENT` holding an entity is refused by the name pattern,
as the form refuses it. `Firm` in `Originator` means no person and `originator_is_firm`;

## Strategic Value Calculation

Strategic-value scoring has a **single source of truth**: `utils/strategic.cjs`.
Every code path uses it — `data.cjs`/CSV import (via a re-export from
`clientAnalyzer.cjs`), `models/clientModel.cjs` (`listWithMetrics`), and
`utils/book.cjs` (the AI's book, which Ask, the brief and the transition plan send). Do NOT reimplement
scoring elsewhere; keep one formula so the dashboard and the AI advisor always
agree.

Current formula (clamped to 0–10):

```
strategicValue = revenueScore*0.50 + stickiness(0–10)*0.50  −  conflictPenalty
revenueScore   = min(10, mostRecentRevenue / 50000)   // $500k → 10
stickiness     = (raw 1–5 pick − 1) / 4 × 10; not rated: UNRATED_STICKINESS = 40 / 9 (≈ 4.44), a fixed stand-in
conflictPenalty: High = 3, Medium = 1, Low = 0
effort         = cadence weight (Daily 5 … As-Needed 0.5) × 1.5 if "handful"
```

`mostRecentRevenue` is the latest year's revenue **for that client**, resolved
from either a `revenues` array (DB shape) or a `revenue` object (frontend
shape); `revenueObjectFromRows(revenues)` builds the object form for every year
on file, and the API responses use it instead of a fixed list of years. The
helpers tolerate both snake_case and camelCase field names so all paths produce
identical numbers. `calculateStrategicValue(client)` with one argument reads
`client.revenues`; passing the rows explicitly is equivalent.

**The unrated stand-in (Tier 2 WP2, S4).** A client with no Stickiness pick
scores with `UNRATED_STICKINESS` (`utils/strategic.cjs`), 40 / 9 exactly: what
the retired `relationship_intensity` gave at its column default of 5, which
every client on production had (Jeff's count, 2026-09-27), so no score moved.
It is a stand-in, not a rating, and the book's legend says so. The retired
columns (`relationship_strength`, `renewal_probability`, `strategic_fit_score`,
`relationship_intensity`) stay in the table for a rollback, but no code reads
or writes them: the scorer, the page's mirror (`resolveStickinessScore` and
its `UNRATED_STICKINESS` in `src/utils/clientMetrics.js`, held equal by
`tests/strategic.test.mjs`), the import (a new client gets the column
defaults) and the camelCase aliases of the API's clients are all without them.
They still come back in every client response, as `c.*` selects them.

**Reporting year vs. score year (D6).** The score uses each client's own
latest revenue year. The dashboard total, cards and charts use the book-wide
reporting year (D4). They differ for a client with no row in the reporting
year: its card shows $0 for that year while its strategic value still reflects
its last year with revenue. Changing that is a scoring-semantics decision, not
Tier 0 work.

> The specific weights are under review. Adjust them in ONE place
> (`utils/strategic.cjs`) and the change propagates everywhere.

### Server Environment Variables (`.env.example` locally, the Render dashboard in production)
- `NODE_ENV` - `production` on Render: Secure SameSite=None cookie, HTTPS redirect, `FRONTEND_URL` as the CORS allowlist
- `PORT` - Server port (defaults to 5000; Render sets its own, and the server binds `0.0.0.0`)
- `DATABASE_URL` - Postgres connection string. Do not put `?sslmode=` in it: `pg` reads it after the `ssl` option, so it overrides `DATABASE_SSL`
- `DATABASE_SSL` - `false` (default, local Postgres), `no-verify` (TLS without certificate checks; Render), or `verify` (with `DATABASE_SSL_CA=<path>` for a private CA). Any other value stops the server at startup
- `JWT_SECRET` - signs the session JWT; rotating it signs every partner out
- `SESSION_TTL` - one lifetime for the JWT and the cookie, `<number><d|h|m>`, default `7d` (D10); an invalid value falls back to `7d` with a startup warning
- `FRONTEND_URL` - the one browser origin allowed in production (`https://gbacpod.com`); unset means no browser origin is allowed, with a startup warning
- `TRUST_PROXY_HOPS` - proxies in front of the app (Render: `1`; default `0`). `req.ip`, and so every IP-keyed rate limit, depends on it: too low and all partners share the proxy's address, too high and a client can choose its own IP with `X-Forwarded-For`
- `BCRYPT_SALT_ROUNDS` - default 12
- `ANTHROPIC_API_KEY` - For AI functionality (Claude API); unset means every AI button reports "not configured"
- `AI_MODEL` - model id for every AI call (default `claude-opus-5`; `claude-sonnet-5` is the cheaper alternative, D7). A model not in `utils/aiCost.cjs`'s `PRICES` logs `costUsd: null`
- `AI_EFFORT` - optional: `low`, `medium`, `high`, `xhigh` or `max`, sent as `output_config.effort` on every AI call (T11); unset means the API's default (`high` on `claude-opus-5`); any other value stops the server at start
- `AI_STREAM_PING_MS` - tests only: the milliseconds between the `: ping` comments on a streamed answer (Tier 1 WP5); unset, blank or anything but a whole number of at least 1 means 15 seconds (`pingInterval`, `utils/sse.cjs`). Do not set it on Render
- `ANTHROPIC_BASE_URL` - local tests only: points the SDK at `tests/helpers/fakeAnthropic.mjs`. Ignored in production, where AI calls always go to `https://api.anthropic.com`; never set it on Render

### Auth, sessions and rate limits (WP3)
- **Cookie:** `authToken`, `HttpOnly`, `Path=/`, `Max-Age` = `SESSION_TTL` (604800 s for `7d`), the same span as the JWT's `exp`. In production `SameSite=None; Secure`, because the API (onrender.com) and the page (gbacpod.com) are different sites and a `Lax` cookie would never reach the API; in development `SameSite=Lax` (page and API are both on localhost, one site). This deviates from D10, which assumed a same-origin API. `res.clearCookie` gets the same attributes.
- **Cross-site requests:** no form-body parser (`express.json` only, 5 MB; a larger body answers 413), CORS allows only the allowlist (`FRONTEND_URL` in production, `localhost:3000`/`5173` in development) and answers other origins without CORS headers rather than with an error, and `server.cjs` refuses POST/PUT/PATCH/DELETE whose `Origin` is neither allowlisted nor the server's own with 403 (`origin_refused` log line). The origin check is what stops a cross-site form from triggering the body-less brief POST (`/api/ai/brief`); do not remove it while the cookie is `SameSite=None`.
- **Rate limits (D11, `middleware/rateLimit.cjs`, express-rate-limit 8):** login 20 per 15 min per IP (`/login` and `/change-password` share it) and 5 failed per 15 min per username (case-folded; successful logins do not count); AI 30 per hour per partner and 300 per day for the firm, one budget across `POST /api/ai/ask`, `POST /api/ai/brief` and `/api/scenarios/*` (none on `GET /api/ai/book` or the saved answers' GETs), mounted after `authenticateToken`. Over the limit: 429 `{ success: false, error: 'Too many requests. Try again later.' }`, which the login page shows verbatim, and a `rate_limited` log line with the limiter and key. Counters are in memory: a redeploy resets them. A custom `keyGenerator` that falls back to the IP must wrap it in `ipKeyGenerator` (the library logs `ERR_ERL_KEY_GEN_IPV6` otherwise). Five wrong passwords lock that username for 15 minutes, including for its owner.
- **Passwords:** `POST /api/auth/change-password` `{ currentPassword, newPassword }` (the header's "Change password" dialog): 200, 400 with the policy's errors, 401 for a wrong current password. `npm run reset:password` for a forgotten one. Neither ends sessions already issued (the JWT is stateless); rotate `JWT_SECRET` to sign everyone out.
- **Database:** a dropped connection logs `{"event":"pg_pool_error",...}`; the pool reconnects on the next query and the process keeps running.
- **Health:** `GET /api/health` needs no sign-in, always answers HTTP 200, and returns `status` (`OK`, or `DEGRADED` when the database query fails or no Anthropic key is set), `timestamp`, `uptimeSeconds`, `environment`, `features` (`["check-file", "transition-plan-roster", "second-chair-assign", "ai-book", "ask-the-book", "ai-answers", "ai-stream", "plain-text", "client-edit-conflict"]`: what this API can do that an older deploy cannot) and `services` (`database`, `anthropic`, `model`). The upload page asks it before **Check file** and sends nothing to an API without `check-file`, which would ignore `dryRun` and import the file; it also shows "Nothing was written" only when the answer carries `dryRun: true`. Scenarios' Stage 2 asks it before its AI plans and sends nothing to an API without `transition-plan-roster`, which would ignore the roster and recommend nobody from it. The Partnership tab's associate split asks it on load and keeps Accept off without `second-chair-assign`. The AI tab's "What the AI is given" panel asks it each time it opens and says "The API has not been updated yet." without `ai-book`, which has no `GET /api/ai/book`. The AI tab asks it on mount and, without `ask-the-book`, says "The API has not been updated yet; try again in a few minutes." and offers no Ask or Brief (an API without it has no `POST /api/ai/ask` or `/api/ai/brief`). The same check shows Recent answers only with `ai-answers` (an API without it saves no answers and has no `GET /api/ai/answers`), and without it shows no list and no error; and streams Ask and the brief only with `ai-stream` (an API without it ignores `Accept: text/event-stream` and answers JSON once the whole answer is written), posting for JSON without it. `plain-text` (Tier 2 WP5) is not for the page, which works with either API: it tells Jeff, before the repair (`deploy/README.md` 7.5), that this API stores text as typed; an API without it escapes every save again, and the repair should not run on it. Add a feature name here when the page starts depending on new API behaviour that an older API would get wrong. A monitor must check the body for `"status":"OK"`, not the status code.

- **What it checks:** the row counts and the dump come from one snapshot; `users`, `clients` and `client_revenues` must exist and `users` must not be empty; `pg_dump`, production and the restore-check server must share a major version (`PG_MAJOR`); the plaintext dump is restored into a throwaway `postgres:$PG_MAJOR` container and every public table's count must match. Only then is it `age`-encrypted. Any failure fails the run, leaves no plaintext and uploads nothing, and GitHub emails the failure.
- **Retention:** each night's `client_portfolio_<UTC stamp>.dump.age` is a workflow artifact kept 90 days. The `age` private key exists only in the password manager.
- **Restore:** `deploy/backup/RESTORE.md` (download, decrypt, scratch restore, count check, production restore on Render, quarterly drill).
- **Self-test:** `.github/workflows/backup-selftest.yml` runs `deploy/backup/selftest.sh` on PostgreSQL 16, 17 and 18 with synthetic data, the happy path and every failure path. Run it locally against a throwaway server only (it creates and drops `pgb_selftest_*` databases): `SELFTEST_SERVER_URL=postgresql://postgres@127.0.0.1:5432 bash deploy/backup/selftest.sh`. A new table in `public` is counted automatically (`ai_answers`, Tier 1 WP4, and `client_changes`, Tier 2 WP6, needed no change), provided the backup role can read it (`pg_read_all_data`, or the default privileges in `deploy/backup/INSTALL.md` step 2); renaming `users`, `clients` or `client_revenues` means updating the required list in `pg-backup.sh`.

## Development Notes

### State Management
- Clients come from the API (`fetchClients()` after sign-in, a CSV import, and every add, update or delete); the store holds them in memory and persists only UI state to localStorage (`partialize` in `portfolioStore.js`). `fetchClients` skips a load while one is in flight, unless `{ force: true }`, which `updateClient` passes after a 409 so the form gets the book as it is now. The client form keeps the client it last filled from (`loaded`: the one opened, then the fresh one after a 409), whose `updated_at_exact` its next save sends, and its history, in its own state
- Scenario state lives in the store (plan P11), so a tab switch keeps it: `successionWorkflow` (`currentStage`: `impact`, `mitigation` or `implementation`; `departingIds`; `choices`, the partner's picks per client, set with `setDepartureChoice`), `transitionPlans` (Stage 2's plans) and Stage 3's execution state. Not persisted (`partialize`), cleared on logout and by `resetSuccessionWorkflow` (the stepper's "Start over"); saving scenarios on the server is later work (review section 7, Tier 2). The Partnership tab's departing flags, redistribution models and custom reassignments are gone (Phase 4); the store's `partners`/`fetchPartners`, derived from the legacy text with an "Unassigned" entry, are gone (PR 5b). Stage 2's plans (`updateTransitionPlan`, `approveTransitionPlans`, which pins each client's seats as choices, `setTransitionPlanStatus`) and Stage 3's `activeTransitions`, `transitionTasks` and `communicationLog` (`startExecution`, `updateTransition`, the task and communication actions) are store state too; Stage 3's counts come from `executionSummary`
- The associate split's picks are the component's own state (they only change what is proposed); accepting goes through the store's `assignSecondChair`, the one write
- The AI tab's answers live in the store (`aiResults`, `{ ask, brief }`, each the route's whole answer, and `aiError`; not persisted, cleared on logout) so switching tabs, which unmounts the tab content, does not discard a paid answer. The request is the store's too (WP5): `askStream(kind, question, { stream })` runs Ask or the brief, streamed (`postStream`) or as JSON, and keeps it in `aiStreaming` (`{ ask, brief }`, each `{ kind, question, text, startedAt, firstTextAt, streamed }` while in flight, else null; `text` updated at most every 100 ms; not persisted, cleared on logout), so a tab switch keeps an answer streaming and its spinner. The answer lands in `aiResults` with the JSON answer's shape (`done`'s `answerId` as `id`), and the saved list reloads when the tab has loaded it (`aiAnswers.loaded`). Only logout aborts a request (the AbortControllers live outside the state); the server finishes and saves it anyway (T15)
- The AI tab's saved answers live in the store too (`aiAnswers`: the list's `items`, `hasMore`, `loaded`, `loadingOlder`, `error`, this month's `summary`, the answers opened as `details` by id, and `openId`; not persisted, cleared on logout), loaded by `fetchAiAnswers` (the first page and the summary), `fetchOlderAiAnswers` and `toggleAiAnswer`. A refresh loses nothing: the list comes back from the API

### AI Integration
- **Every Anthropic call goes through `services/anthropic.cjs`.** It owns the one
  client and the one model constant `AI_MODEL` (env `AI_MODEL`, default
  `claude-opus-5`, D7). Routes call
  `complete({ system, prompt, maxTokens, userId, label, onStart, onText })` and never
  construct a client or call the Messages API themselves;
  `tests/ai-grep.test.mjs` fails if `messages.create(`, `messages.stream(`,
  `countTokens(` or `new Anthropic(` appears anywhere else, or `betas`,
  `fallbacks` or `output_config` outside the service.
- SDK `@anthropic-ai/sdk` 0.128.0 (Tier 1 WP1, `docs/plans/tier-1.md` T2). The
  service is a factory, `createService({ apiKey, model, effort, fetch, baseURL })`;
  the module exports the default instance, built from the environment at start
  (`AI_MODEL`, `isConfigured`, `complete`), plus `createService`,
  `parseResponse` and `describeError`. Every call streams from Anthropic
  (`client.beta.messages.stream(...)`, then `finalMessage()`; `onStart` is
  called once, with nothing, on the stream's first event, after the SDK's
  retries of an HTTP error and before any text, which is when Ask and the brief
  open their own stream (WP5); `onText` gets each text delta; an error either
  throws is logged once, as `ai_on_start_error` or `ai_on_text_error`, and
  never stops the call). The request carries `model`, `max_tokens`, `system` (a
  string, or `{ type: 'text', text, cache_control? }` blocks passed through
  unchanged) and one user turn; plus, only while the model is in
  `FALLBACK_MODELS` (`claude-opus-5`), `fallbacks: 'default'` with the beta
  `server-side-fallback-2026-07-01` (T10); plus, only when `AI_EFFORT` is set,
  `output_config: { effort }` (T11). Nothing else: no sampling parameters, no
  `thinking` (the model thinks by default, and `max_tokens` caps thinking and
  answer together), no tools, no prefill. The SDK's `timeout` (180 s) bounds the
  wait for an answer to start, not the answer (checked with Node's own fetch;
  the module comment has the details). In production the address is always
  `https://api.anthropic.com`: `ANTHROPIC_BASE_URL` is ignored there with an
  `anthropic_base_url_ignored` warning at start (T17). Only the API key is sent
  (`authToken: null`).
- `parseResponse()` collects text by content-block type, skipping `thinking` and
  `fallback` blocks; text on either side of a `fallback` block (a mid-stream
  decline the fallback model continued) is joined with nothing between. It
  flags `truncated` (`stop_reason: max_tokens`) and `refused`; a refusal nothing
  rescued returns empty text, whatever streamed before it, and
  `refusalCategory` from `stop_details`. It adds `servedBy` (the message's
  `model`), `fellBack` (a `fallback_message` entry in `usage.iterations`), the
  counts summed over the call's attempts as `tokens`
  (`{ inputTokens, outputTokens, cacheReadTokens, cacheWrite5mTokens, cacheWrite1hTokens, iterations }`)
  and keeps the raw `usage`. `complete()` adds `costUsd` and `pricesReadOn`. Ask
  and the brief answer as `POST /api/ai/ask` above; a transition plan answers
  `{ success: true, plan: { ..., truncated, refused }, answerId, saved, timestamp }`;
  the UI shows "The response was cut off; ask a narrower question." when
  `truncated` is true and "The AI declined to answer this request." when
  `refused` is.
- Errors: `describeError(err)` maps SDK errors to a status and a message a
  partner can act on (503 not configured, 429 rate limited, 504 unreachable,
  503 upstream 5xx, 502 bad key or rejected request). An `error` event in the
  middle of a stream arrives as an `APIError` with no status and a `type`:
  `overloaded_error` and `api_error` give 503, `rate_limit_error` 429, another
  type 502 naming it. Routes answer `{ success: false, error }`;
  `apiErrorMessage()` in `src/api.js` extracts that text on the frontend.
- One structured log line per call:
  `{"event":"ai_call",label,userId,model,servedBy,fellBack,stop,refusalCategory,inputTokens,outputTokens,cacheReadTokens,cacheWriteTokens,costUsd,ms}`
  (`model` is the one requested; `ai_error` with `status`, `type` and `message`
  on failure). `costUsd` is an estimate from list prices in
  `utils/aiCost.cjs` (pure): `PRICES` per model, `PRICES_READ_ON`, and
  `callCost(usage, model, { declined })`, which prices each attempt in
  `usage.iterations` at its own model (cache writes 1.25x for 5 minutes and 2x
  for 1 hour, reads 0.1x) and follows Anthropic's refusal billing rule (a
  refusal before any output is billed only for `bio`, `frontier_llm` and
  `reasoning_extraction`). A model without a price gives `costUsd: null` and an
  `ai_cost_unknown_model` line, never a guess: add the model to `PRICES` when
  `AI_MODEL` or a fallback target changes. The Anthropic Console is the bill.
- Saved answers (Tier 1 WP4, T12, T13): every route that calls `complete()`
  saves its answer in `ai_answers` after the call returns, through
  `answerRow` (`utils/aiAnswers.cjs`) and `saveAnswer`
  (`models/aiAnswerModel.cjs`): the kind, the question or the client, the
  answer (empty for a refusal, with its category), who asked, the model
  requested and the one that served, the flags, the tokens by kind, the
  cost and `prices_read_on` as `complete()` gave them, the book's SHA-256,
  the reporting year and the call's duration. An AI error is logged, not
  saved. A failed save never loses an answer the partner has paid for: the
  route returns it with `saved: false` and logs one
  `{"event":"ai_answer_save_failed",label,userId,kind,code,message}` line. A
  new AI route saves its answers the same way, with a new `kind` in the
  table's `CHECK` and `KINDS`. Nobody can edit or delete a saved answer in
  Tier 1; every partner sees every one.
- Testing without a key (`docs/plans/tier-1.md` section 4):
  `tests/fixtures/anthropic/` holds recorded streams (`*.sse`, written from the
  documented wire format) and HTTP errors (`*.json`);
  `tests/helpers/fakeAnthropic.mjs` exports `fakeFetch(queue)` for
  `createService({ apiKey: 'test', fetch })` and `startFakeAnthropic()`, an
  http server on 127.0.0.1 that answers `POST /v1/messages` from a queue (it
  can hold a stream open after `pauseAfter` events, for `pauseMs` or `until` a
  promise settles, and space events `gapMs` apart) and records each request. As a script,
  `node tests/helpers/fakeAnthropic.mjs --port 5099`, it answers every request

  ANTHROPIC_BASE_URL=http://127.0.0.1:5099 node server.cjs`.

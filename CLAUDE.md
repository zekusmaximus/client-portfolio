## Development Commands

### Frontend Development
- `VITE_API_BASE_URL=http://localhost:5000 npm run dev` - Vite dev server on http://localhost:5173 (PowerShell: `$env:VITE_API_BASE_URL = 'http://localhost:5000'; npm run dev`). Without the variable the page calls relative `/api`, which Vite does not proxy
- `VITE_API_BASE_URL=https://gbacpod.com npm run build:prod` - the production build CI and Netlify run (`NODE_ENV=production vite build`, POSIX syntax; on Windows use `npx vite build`, production is Vite's default mode). A production build refuses a missing or non-`https://` `VITE_API_BASE_URL`
- `npm run build` - `vite build` without the `NODE_ENV` prefix; `npm run preview` serves `dist/`
- `npm run lint` - Run ESLint on JS/JSX/CJS files (errors fail the gate, warnings are informational; 3 `exhaustive-deps` warnings are expected, in `App.jsx` and `DashboardView.jsx`, D3; the other four went with the components Phase 4 deleted)
- `npm run security:audit` / `npm run security:audit-fix` - `npm audit` / non-breaking `npm audit fix`; never `--force` (the two remaining advisories, Vite and esbuild, are dev-only and need Vite 8; `npm audit --omit=dev` reports none; `deploy/README.md` section 12)

## Architecture Overview

This is a **Client Portfolio Optimization Dashboard** for government relations attorneys, consisting of:

### Frontend (React + Vite)
- **Framework**: React 18 with Vite bundler
- **State Management**: Zustand (`src/portfolioStore.js`); clients come from the API, and only UI state is persisted to localStorage
- **UI Library**: Shadcn/UI components with Tailwind CSS
- **Charts**: Recharts for data visualizations
- **Main Entry**: `src/main.jsx` renders `src/App.jsx`

### Backend (Node.js + Express)
- **Server**: Express.js server in `server.cjs` (`PORT`, default 5000; Render sets its own). API only: the page is served by Netlify, and Express serves no static files. **Start-up** (Tier 3 WP3, candidate (o)): the connection test (`SELECT 1`) and `init-db.sql` run first, and only then does it listen, printing `Testing database connection...`, `PostgreSQL connection OK`, `Initializing database tables...`, `Database tables initialized`, `Server running on port <n>` and `Environment: <env>` in that order (runbook 9.2), so a deploy takes requests only once its tables exist. A failure logs `Database initialization failed:` (through `logError`); in production it then exits without listening, and in development it still listens without a database. Until WP3 it listened at once, and `Server running on port` came second. `.env` is read with `require('dotenv').config({ quiet: true })` here and in every script, so no dotenv banner is printed (until WP3 all but `scripts/eval-ai.cjs` printed one on the standard output)

#### Data Flow
1. CSV upload → `data.cjs` processes via `clientAnalyzer.cjs`; the pure helpers in `utils/csvImport.cjs` read the years and the sheet's optional columns from the header, check the file (`checkSheet`) and plan the writes
2. Clients live in Postgres; the store loads them with `fetchClients()` after sign-in and after every write. localStorage keeps only UI state (`optimizationParams`, `currentView`, `isModalOpen`, `selectedClient`)
3. Strategic value calculations use the single scorer in `utils/strategic.cjs` (re-exported by `clientAnalyzer.cjs`)

**CSV year rule (D5).** No revenue year is hard-coded anywhere. A CSV's revenue
columns are its `YYYY Contracts` headers (case-insensitive), and the file is
authoritative for exactly those years: an amount > 0 upserts the
`(client, year)` row, a blank or `$0` cell deletes it, and years the file does
not mention are left untouched. A 2026-only sheet therefore updates 2026 and
keeps 2023–2025; a corrected sheet can still zero out a year. A file with no
year columns writes no revenue and returns the validation warning
``No `YYYY Contracts` columns found; revenue not changed.``
The import deletes every `(client, year)` pair the file names and inserts the
positive amounts, as the client form writes revenue; it uses no `ON CONFLICT`
and no type cast on `client_id` (production's older tables, under File
Structure). `processCSVData` attaches the file's years to every client as `revenueYears`,
and `POST /api/data/process-csv` returns them as `summary.revenueYears`.

**Import sheet (P8; `docs/plans/people-and-second-chair.md` section 3).** Beside
`CLIENT` and the years, the only structural columns, a CSV may carry `Lead`,
`Second Chair`, `Originator`, `Credit To Firm`, `Stickiness`, `Cadence`,
`Handful`, `Conflict Risk`, `Practice Area` and `Notes`, matched
case-insensitively and trimmed (`CLIENT` still matches exactly). A
`Contract Period` column is ignored like any unknown header (P13): a sheet that
has it imports exactly as one without it. As with the years, the file is authoritative for exactly the columns
it has. A column it lacks leaves that field as it is: the columns the import has
always written keep their preserve logic, and `stickiness`, `high_maintenance`
and the four people columns are left out of the `UPDATE` (`importWriteColumns`),
so a file without the new columns writes what it wrote before. A blank cell in a
column the file has clears the field: no second chair, no originator,
stickiness NULL, Handful false, Conflict Risk `Medium`, practice areas `{}`,
notes and cadence `''`. Names resolve against the People list regardless of case,
as the sheet spells them: since Tier 2 WP5 every cell is stored as typed,
trimmed, and neither escaped nor decoded (until then the request sanitizer
escaped each cell and `decodeHTMLEntities` decoded it again, which also
decoded a literal entity typed in a cell, `&#169;` to ©, and checked `CLIENT`'s
length escaped). A `CLIENT` holding an entity is refused by the name pattern,
as the form refuses it. `Firm` in `Originator` means no person and `originator_is_firm`;
`Credit To Firm` `Y` sets the flag, and without that column a person in
`Originator` keeps the stored flag. The rules are `validateAssignment` and
`legacyText` from `utils/people.cjs`; a people column the file lacks is checked
with the stored value, so a new lead who is the kept second chair is refused.
`Second Chair`, `Originator` and `Credit To Firm` need a `Lead` column. Any
problem refuses the whole file before anything is written: 400
`{ success: false, error, errors: [{ row, client, message }] }`, rows numbered as
a spreadsheet shows them (the header is row 1, and header problems are listed as
row 1). The problems: a name not on the list, a missing lead or one who is not an
active partner, a second chair who is the lead or inactive, a value outside its
column's vocabulary (the lists are `utils/clientRules.cjs`'s, which the client
form's writes apply too; Stickiness `1`-`5`; Cadence `Daily`/`Weekly`/`Monthly`/
`Quarterly`/`As-Needed`; Conflict Risk `Low`/`Medium`/`High`; Handful and Credit
To Firm `Y` or blank; Practice Area from the form's twelve, `;`-separated; all
case-insensitive), a column given twice, a people column without `Lead`, an
amount over 1,000,000,000 in any `YYYY Contracts` column (`REVENUE_AMOUNT_MAX`,
the client form's limit; Tier 3 WP2, candidate (w): until then the import
stored it, and from 10,000,000,000 up failed in `NUMERIC(12, 2)` with a 500),
and a `CLIENT` named twice regardless of case or shared by two stored clients
(below), which refuses every file, with or without the new columns. Contract periods no longer produce `validation.issues`;
the list stays in the response and still does not block.
**Client names** match stored clients regardless of case and unescaped. A client
saved through the client form before Tier 2 WP5 was stored HTML-escaped by the
request sanitizer (`Barnes &amp; Noble`, `O&#x27;Brien`; escaped again by each
save that sent the stored text back), and stays so until the repair
(`npm run unescape:book`), so the import selects the rows with
`LOWER(unescapeStoredSql('name')) = ANY($1)` and keys them with `unescapeStored`
(`utils/escaping.cjs`; one list of replacements, and `import-db` checks the SQL
and the JavaScript agree on PostgreSQL). The client form's writes compare a
stored name the same way (`utils/clientNames.cjs`, Tier 3 WP2): `POST` and a
renaming `PUT` refuse a name another client has, so they no longer make a pair
the import would then refuse (under API Routes, above); the import takes their
client-name lock first too, before it reads the stored names. Nothing else
compares a stored name.
A matched client is updated and its name written in the sheet's spelling, so an
import repairs the stored names of the clients it names; no migration rewrites
names (`init-db.sql` runs at every start, and each pass would strip another
layer): the escaped text the sanitizer left in names, notes and the legacy
people text is repaired once by the guarded script `scripts/unescape-book.cjs`
(WP5), and `unescapeStored` stays here as a guard. A `CLIENT` two stored clients share this way (for
example the duplicate the old exact match created) refuses its row: the import
cannot tell which one to update, and a partner deletes one on Client Details.
The page shows, fills and writes names and notes as stored, which since Tier 2
WP5 is as typed: the client form (`clientFormData` in
`src/utils/clientForm.js`), Scenarios' transition sheet, the book sheet and
every view (`formatClientName`, `src/utils/textUtils.js`, only trims). Until
WP5's second PR the page undid the escaping with its own copy of
`unescapeStored` and the views decoded one level (a `textarea`'s `innerHTML`);
Jeff's repair preview on 2026-09-28 found nothing stored escaped, so both went,
and a literal `&lt;` a partner types in a note now round-trips unchanged. If a
restored backup ever brings escaped text back, the page shows it raw: run the
repair again (`npm run unescape:book`, runbook 7.5).
**The book as a sheet.** Data Upload's "Download the book as a sheet" builds, in
the page and without an API call, the sheet the import reads with every client's
current values (`buildBookSheet` in `src/utils/bookSheet.js`, pure;
`exportBookSheet` downloads `client_book_<date>.csv`), so that importing it
unchanged changes nothing; it is the master sheet for a new year's revenue or a
bulk correction. Columns: `CLIENT`, a `YYYY Contracts` column for every year in
which any client has an amount above 0 (`revenueYearsOnFile`), then the ten
optional columns in section 3's order. Each cell is what the import reads back
into the stored value: amounts bare (`40000`, `30000.50`), blank for none; people
as the People list spells them; `Firm` in Originator for a firm credit without a
person and `Y` in Credit To Firm whenever the flag is set; Stickiness 1 to 5 or
blank; the stored cadence and conflict risk; `Y` or blank for Handful; practice
areas joined with `;`; client names and notes as stored. Rows are
sorted by name. Cells are quoted as `sheetCell` quotes them, with no formula
guard, and the download adds a BOM so Excel reads UTF-8 (PapaParse drops it). A
client whose lead is missing or not an active partner, or whose second chair is
inactive, is written as the book has it (a blank Lead, or the person's name), so
Check file refuses those rows with the import's own message; the page lists them
above the download (`attention`). Leaving them out would make a master sheet that
silently lacks clients and a revenue import that silently skips them. A round
trip changes nothing: since Tier 2 WP6 the import compares each matched client's
fields and revenue with what the file would write (as the history compares them,
`utils/clientChanges.cjs`) and writes only the clients that differ, so an
unchanged sheet writes no client, moves no `updated_at` (a client form left open
still saves) and logs nothing; `summary.updatedClients` still counts the stored
clients the file names, and `summary.changedClients` counts those it changed.
For a client it does write, the ids and timestamps of its revenue rows are new
(the import deletes and re-inserts every year the file names) and a stored `$0`
row in a year on file is removed (the year rule reads `$0` as none); a client
whose only difference is such a row is not written, and keeps it. Until WP6
every matched client was rewritten and its `updated_at` moved.
With `dryRun: true` (the page's **Check file**) every check and
every write runs in the same transaction, which is then rolled back: the same
400, or `{ success: true, dryRun: true, validation, summary }` with nothing
written; `dryRun` must be a boolean (400 otherwise). Every successful import or
check returns `summary.revenueTotals`, each year's total of the file's amounts over
every client it names, written or not (`revenueTotals` in `utils/csvImport.cjs`), because the page totals only
the reporting year and the runbook compares every year with the sheet. The pure helpers are `findSheetColumns`, `readSheetRow`,
`resolveSheetPeople`, `checkSheet`, `indexStoredClients`, `importWriteColumns` and `valuesList` in
`utils/csvImport.cjs`; a successful import returns the columns it read as
`summary.sheetColumns`.

**Reporting year (D4).** The frontend derives `reportingYear`, the latest year
in which any client has a revenue row with amount > 0, falling back to the

## Strategic Value Calculation

Strategic-value scoring has a **single source of truth**: `utils/strategic.cjs`.
Every code path uses it — `data.cjs`/CSV import (via a re-export from
`clientAnalyzer.cjs`), `models/clientModel.cjs` (`listWithMetrics`), and
`utils/book.cjs` (the AI's book, which Ask, the brief and the transition plan send). Do NOT reimplement
scoring elsewhere; keep one formula so the dashboard and the AI advisor always
agree.

Current formula (clamped to 0–10):

```
strategicValue = revenueScore*0.50 + stickiness(0–10)*0.50  −  conflictPenalty
revenueScore   = min(10, mostRecentRevenue / 50000)   // $500k → 10
stickiness     = (raw 1–5 pick − 1) / 4 × 10; not rated: UNRATED_STICKINESS = 40 / 9 (≈ 4.44), a fixed stand-in
conflictPenalty: High = 3, Medium = 1, Low = 0
effort         = cadence weight (Daily 5 … As-Needed 0.5) × 1.5 if "handful"
```

`mostRecentRevenue` is the latest year's revenue **for that client**, resolved
from either a `revenues` array (DB shape) or a `revenue` object (frontend
shape); `revenueObjectFromRows(revenues)` builds the object form for every year
on file, and the API responses use it instead of a fixed list of years. The
helpers tolerate both snake_case and camelCase field names so all paths produce
identical numbers. `calculateStrategicValue(client)` with one argument reads
`client.revenues`; passing the rows explicitly is equivalent.

**The unrated stand-in (Tier 2 WP2, S4).** A client with no Stickiness pick
scores with `UNRATED_STICKINESS` (`utils/strategic.cjs`), 40 / 9 exactly: what
the retired `relationship_intensity` gave at its column default of 5, which
every client on production had (Jeff's count, 2026-09-27), so no score moved.
It is a stand-in, not a rating, and the book's legend says so. The retired
columns (`relationship_strength`, `renewal_probability`, `strategic_fit_score`,
`relationship_intensity`) stay in the table for a rollback, but no code reads
or writes them: the scorer, the page's mirror (`resolveStickinessScore` and
its `UNRATED_STICKINESS` in `src/utils/clientMetrics.js`, held equal by
`tests/strategic.test.mjs`), the import (a new client gets the column
defaults) and the camelCase aliases of the API's clients are all without them.
They still come back in every client response, as `c.*` selects them.

**Reporting year vs. score year (D6).** The score uses each client's own
latest revenue year. The dashboard total, cards and charts use the book-wide
reporting year (D4). They differ for a client with no row in the reporting
year: its card shows $0 for that year while its strategic value still reflects
its last year with revenue. Changing that is a scoring-semantics decision, not
Tier 0 work.

> The specific weights are under review. Adjust them in ONE place
> (`utils/strategic.cjs`) and the change propagates everywhere.

**Succession metrics (Tier 2 WP7, S11).** `utils/succession.cjs` (pure)
computes each client's `relationshipType`, `transitionComplexity` and
`successionRisk` from its nested people and the scorer's figures, and every
client response carries them; the page's copy, `src/utils/successionUtils.js`,
serves only the client form's preview and a client from an API older than WP7,
and `tests/succession.test.mjs` holds the two equal figure for figure (the
scores are rounded, so each sum runs in the same order on both sides). The
rules, as Jeff approved them on 2026-09-27:

```
relationshipType     orphaned   no lead (whatever the stored legacy text says)
                     shared     a second chair and stickiness >= 7 of 10 (picks 4 and 5)
                     primary    the lead is the recorded originator, no second chair
                                (whatever originator_is_firm says)
                     secondary  otherwise
transitionComplexity round(min(10, effort / 7.5 × 10) × 0.3
                           + 1.5 if a practice area holds healthcare, energy or financial
                           + 1 if conflict risk is High), capped at 10
successionRisk       round(type (primary 3, secondary 2, shared 1, orphaned 5)
                           + (6 − stickiness) when stickiness < 6
                           + complexity × 0.3), capped at 10
```

Stickiness is 0 to 10 from the raw pick (`getStickiness`), 40 / 9 when there is
none, on both sides, never the API's rounded `stickinessScore`; effort is the
client's `effort`, else the scorer's (`clientEffort`). Cadence counts only
through effort (until WP7 it was also added on its own). The form's practice
area `Financial` counts as a complex area since Tier 3 WP2 (U6 (b), approved
by Jeff on 2026-09-29): until then the third area was `financial services`,
which `Financial` does not contain, so it added nothing. `financial` matches
either, as part of the area's name in any case; a Financial client's
complexity gains 1.5 before rounding, and its risk 0.3 of the complexity's
change. The transition plan
computes the metrics from the book's entry for its client (`bookEntryMetrics`,
equal to the client response's for every value a write allows). No
`/api/health` feature name: the store keeps the API's figures and computes
them with the same rules only when a client has none (`withSuccessionMetrics`),
so the page shows the same figures on either API.

### Server Environment Variables (`.env.example` locally, the Render dashboard in production)
- `NODE_ENV` - `production` on Render: Secure SameSite=None cookie, HTTPS redirect, `FRONTEND_URL` as the CORS allowlist
- `PORT` - Server port (defaults to 5000; Render sets its own, and the server binds `0.0.0.0`)
- `DATABASE_URL` - Postgres connection string. Do not put `?sslmode=` in it: `pg` reads it after the `ssl` option, so it overrides `DATABASE_SSL`
- `DATABASE_SSL` - `false` (default, local Postgres), `no-verify` (TLS without certificate checks; Render), or `verify` (with `DATABASE_SSL_CA=<path>` for a private CA). Any other value stops the server at startup
- `JWT_SECRET` - signs the session JWT; rotating it signs every partner out
- `SESSION_TTL` - one lifetime for the JWT and the cookie, `<number><d|h|m>`, default `7d` (D10); an invalid value falls back to `7d` with a startup warning
- `FRONTEND_URL` - the one browser origin allowed in production (`https://gbacpod.com`); unset means no browser origin is allowed, with a startup warning
- `TRUST_PROXY_HOPS` - proxies in front of the app (Render: `1`; default `0`). `req.ip`, and so every IP-keyed rate limit, depends on it: too low and all partners share the proxy's address, too high and a client can choose its own IP with `X-Forwarded-For`
- `BCRYPT_SALT_ROUNDS` - default 12
- `ANTHROPIC_API_KEY` - For AI functionality (Claude API); unset means every AI button reports "not configured"
- `AI_MODEL` - model id for every AI call (default `claude-opus-5`; `claude-sonnet-5` is the cheaper alternative, D7). A model not in `utils/aiCost.cjs`'s `PRICES` logs `costUsd: null`
- `AI_EFFORT` - optional: `low`, `medium`, `high`, `xhigh` or `max`, sent as `output_config.effort` on every AI call (T11); unset means the API's default (`high` on `claude-opus-5`); any other value stops the server at start
- `AI_STREAM_PING_MS` - tests only: the milliseconds between the `: ping` comments on a streamed answer (Tier 1 WP5); unset, blank or anything but a whole number of at least 1 means 15 seconds (`pingInterval`, `utils/sse.cjs`). Do not set it on Render

### Auth, sessions and rate limits (WP3)
- **Cookie:** `authToken`, `HttpOnly`, `Path=/`, `Max-Age` = `SESSION_TTL` (604800 s for `7d`), the same span as the JWT's `exp`. In production `SameSite=None; Secure`, because the API (onrender.com) and the page (gbacpod.com) are different sites and a `Lax` cookie would never reach the API; in development `SameSite=Lax` (page and API are both on localhost, one site). This deviates from D10, which assumed a same-origin API. `res.clearCookie` gets the same attributes.
- **Cross-site requests:** no form-body parser (`express.json` only, 5 MB; a larger body answers 413), CORS allows only the allowlist (`FRONTEND_URL` in production, `localhost:3000`/`5173` in development) and answers other origins without CORS headers rather than with an error, and `server.cjs` refuses POST/PUT/PATCH/DELETE whose `Origin` is neither allowlisted nor the server's own with 403 (`origin_refused` log line). The origin check is what stops a cross-site form from triggering the body-less brief POST (`/api/ai/brief`); do not remove it while the cookie is `SameSite=None`.
- **Rate limits (D11, `middleware/rateLimit.cjs`, express-rate-limit 8):** login 20 per 15 min per IP (`/login` and `/change-password` share it) and 5 failed per 15 min per username (case-folded; successful logins do not count); AI 30 per hour per partner and 300 per day for the firm, one budget across `POST /api/ai/ask`, `POST /api/ai/brief` and `POST /api/scenarios/transition-plan` (none on `GET /api/ai/book`, the saved answers' GETs or the saved scenarios' routes, which until Tier 2 WP8 sat behind them with every `/api/scenarios` route), mounted after `authenticateToken`. Over the limit: 429 `{ success: false, error: 'Too many requests. Try again later.' }`, which the login page shows verbatim, and a `rate_limited` log line with the limiter and key. Counters are in memory: a redeploy resets them. A custom `keyGenerator` that falls back to the IP must wrap it in `ipKeyGenerator` (the library logs `ERR_ERL_KEY_GEN_IPV6` otherwise). Five wrong passwords lock that username for 15 minutes, including for its owner.
- **Passwords:** `POST /api/auth/change-password` `{ currentPassword, newPassword }` (the header's "Change password" dialog): 200, 400 with the policy's errors, 401 for a wrong current password. `npm run reset:password` for a forgotten one. Neither ends sessions already issued (the JWT is stateless); rotate `JWT_SECRET` to sign everyone out.
- **Database:** a dropped connection logs `{"event":"pg_pool_error",...}`; the pool reconnects on the next query and the process keeps running.
- **Failures:** every route's 500, the error middleware's and a failed start log one line through `logError` (`utils/errorLog.cjs`, Tier 3 WP2): the label (`Error updating client`, `Error updating person`, `ai_ask failed`, `❌  Database initialization failed`, ...) and the error's `code`, `message` and, where PostgreSQL sets them, `constraint`, `table` and `column`, as JSON. Never `detail` (for a refused row, the whole row, a note included), `where` or the error object, so no stack trace either (until WP2 every such site but the saved scenarios' printed the error object). A new route logs its failure the same way; `tests/error-log.test.mjs` fails otherwise.

### AI Integration
- **Every Anthropic call goes through `services/anthropic.cjs`.** It owns the one
  client and the one model constant `AI_MODEL` (env `AI_MODEL`, default
  `claude-opus-5`, D7). Routes call
  `complete({ system, prompt, history, maxTokens, userId, label, onStart, onText })` and never
  construct a client or call the Messages API themselves;
  `tests/ai-grep.test.mjs` fails if `messages.create(`, `messages.stream(`,
  `countTokens(` or `new Anthropic(` appears anywhere else, or `betas`,
  `fallbacks` or `output_config` outside the service; and, from Tier 2 WP10,
  if a thread's `history` is built anywhere but `threadHistory`
  (`utils/aiThreads.cjs`) or passed to `complete()` anywhere but
  `routes/ai.cjs`, or a `cache_control` is set anywhere but the book's block
  (`utils/askPrompts.cjs`) and the thread's automatic marker (the service).
- SDK `@anthropic-ai/sdk` 0.128.0 (Tier 1 WP1, `docs/plans/tier-1.md` T2). The
  service is a factory, `createService({ apiKey, model, effort, fetch, baseURL })`;
  the module exports the default instance, built from the environment at start
  (`AI_MODEL`, `isConfigured`, `complete`), plus `createService`,
  `parseResponse` and `describeError`. Every call streams from Anthropic
  (`client.beta.messages.stream(...)`, then `finalMessage()`; `onStart` is
  called once, with nothing, on the stream's first event, after the SDK's
  retries of an HTTP error and before any text, which is when Ask and the brief
  open their own stream (WP5); `onText` gets each text delta; an error either
  throws is logged once, as `ai_on_start_error` or `ai_on_text_error`, and
  never stops the call). The request carries `model`, `max_tokens`, `system` (a
  string, or `{ type: 'text', text, cache_control? }` blocks passed through
  unchanged) and one user turn (`prompt`), after a follow-up's earlier turns
  (`history`, Tier 2 WP10, sent exactly as given) and then with the automatic
  cache marker, a top-level `cache_control: { type: 'ephemeral' }`, so the
  next follow-up reads the history from the cache (the claude-api skill's
  pattern for a growing conversation: one explicit marker on the static
  prefix, the book, and automatic caching for the tail; at most two of the
  four breakpoints); plus, only while the model is in
  `FALLBACK_MODELS` (`claude-opus-5`), `fallbacks: 'default'` with the beta
  `server-side-fallback-2026-07-01` (T10); plus, only when `AI_EFFORT` is set,
  `output_config: { effort }` (T11). Nothing else: no sampling parameters, no
  `thinking` (the model thinks by default, and `max_tokens` caps thinking and
  answer together), no tools, no prefill. The SDK's `timeout` (180 s) bounds the
  wait for an answer to start, not the answer (checked with Node's own fetch;
  the module comment has the details). In production the address is always
  `https://api.anthropic.com`: `ANTHROPIC_BASE_URL` is ignored there with an
  `anthropic_base_url_ignored` warning at start (T17). Only the API key is sent
  (`authToken: null`).
- `parseResponse()` collects text by content-block type, skipping `thinking` and
  `fallback` blocks; text on either side of a `fallback` block (a mid-stream
  decline the fallback model continued) is joined with nothing between. It
  flags `truncated` (`stop_reason: max_tokens`) and `refused`; a refusal nothing
  rescued returns empty text, whatever streamed before it, and
  `refusalCategory` from `stop_details`. It adds `servedBy` (the message's
  `model`), `fellBack` (a `fallback_message` entry in `usage.iterations`), the
  counts summed over the call's attempts as `tokens`
  (`{ inputTokens, outputTokens, cacheReadTokens, cacheWrite5mTokens, cacheWrite1hTokens, iterations }`)
  and keeps the raw `usage`. `complete()` adds `costUsd` and `pricesReadOn`. Ask
  and the brief answer as `POST /api/ai/ask` above; a transition plan answers
  `{ success: true, plan: { ..., truncated, refused }, answerId, saved, timestamp }`;
  the UI shows "The response was cut off; ask a narrower question." when
  `truncated` is true and "The AI declined to answer this request." when
  `refused` is.
- Errors: `describeError(err)` maps SDK errors to a status and a message a
  partner can act on (503 not configured, 429 rate limited, 504 unreachable,
  503 upstream 5xx, 502 bad key or rejected request). An `error` event in the
  middle of a stream arrives as an `APIError` with no status and a `type`:
  `overloaded_error` and `api_error` give 503, `rate_limit_error` 429, another
  type 502 naming it. Routes answer `{ success: false, error }`;
  `apiErrorMessage()` in `src/api.js` extracts that text on the frontend.
- One structured log line per call:
  `{"event":"ai_call",label,userId,model,servedBy,fellBack,stop,refusalCategory,inputTokens,outputTokens,cacheReadTokens,cacheWriteTokens,costUsd,ms}`
  (`model` is the one requested; `ai_error` with `status`, `type` and `message`
  on failure). `costUsd` is an estimate from list prices in
  `utils/aiCost.cjs` (pure): `PRICES` per model, `PRICES_READ_ON`, and
  `callCost(usage, model, { declined })`, which prices each attempt in
  `usage.iterations` at its own model (cache writes 1.25x for 5 minutes and 2x
  for 1 hour, reads 0.1x) and follows Anthropic's refusal billing rule (a
  refusal before any output is billed only for `bio`, `frontier_llm` and
  `reasoning_extraction`). A model without a price gives `costUsd: null` and an
  `ai_cost_unknown_model` line, never a guess: add the model to `PRICES` when
  `AI_MODEL` or a fallback target changes. The Anthropic Console is the bill.
- Model and effort from real answers (Tier 2 WP11, S16): `scripts/eval-ai.cjs`
  (under Backend Development, above; runbook 7.6) asks saved questions again
  under `claude-opus-5` at the API's default effort and at `medium`, and
  `claude-opus-5-5` when Jeff asks, through `createService`, and writes the
  answers side by side; it saves nothing. The model (D7) and the effort are
  Jeff's to choose from it. The change his choice needs is `PRICES` and
  `FALLBACK_MODELS` in code and `AI_EFFORT` on Render; per the `claude-api`
  skill, `claude-opus-5-5` takes `fallbacks: "default"` too and defaults to
  effort `medium` (so a switch sets `AI_EFFORT` explicitly), reads the thinking
  blocks `claude-opus-5` wrote in WP10's threads, while `claude-opus-5` drops
  `claude-opus-5-5`'s (unbilled) after a rollback, and caches are per model, so
  the first answer on each model after a switch writes the book again.
- Saved answers (Tier 1 WP4, T12, T13): every route that calls `complete()`
  saves its answer in `ai_answers` after the call returns, through
  `answerRow` (`utils/aiAnswers.cjs`) and `saveAnswer`
  (`models/aiAnswerModel.cjs`): the kind, the question or the client, the
  answer (empty for a refusal, with its category), who asked, the model
  requested and the one that served, the flags, the tokens by kind, the
  cost and `prices_read_on` as `complete()` gave them, the book's SHA-256,
  the reporting year and the call's duration. An AI error is logged, not
  saved. A failed save never loses an answer the partner has paid for: the
  route returns it with `saved: false` and logs one
  `{"event":"ai_answer_save_failed",label,userId,kind,code,message}` line. A
  new AI route saves its answers the same way, with a new `kind` in the
  table's `CHECK` and `KINDS`. Nobody can edit or delete a saved answer;
  every partner sees every one, and from Tier 2 WP10 any partner can hide one
  from the list (S15). An Ask or a brief whose answer is whole is saved with
  its turn (`content`) and a follow-up with its `parent_id` (S14).
- Follow-up questions (Tier 2 WP10, S14, lifting T7): a thread is a chain,
  each follow-up's parent the answer it follows, at most five follow-ups
  after the first answer (`FOLLOW_UP_MAX`), counted from the thread's first
  answer; two follow-ups to one answer make two threads that share their
  start. A follow-up's request is append-only, as the claude-api skill
  requires: the same two system blocks, then each earlier turn's user
  message as it was sent (with the day it was asked) and its assistant
  message as the API returned its content blocks, thinking blocks and their
  signatures included (a model reads only the blocks it can and the API
  drops the rest unbilled, so nothing is stripped), then the new question;
  after a fallback in the middle of an answer, only its text blocks (and the
  `fallback` marker) go back from before the last boundary (`replayBlocks`,
  the skill's echo rule). The same saved turns always give the same bytes,
  so each follow-up's request begins with the one before it; the fake
  server's recorded requests show it (`tests/ai-threads.test.mjs`,
  `tests/routes.test.mjs`). A follow-up is refused (409) when the system
  blocks' hash differs from the thread's: the book (or the instructions)
  changed, and replaying the earlier turns after other system blocks would
  edit the conversation's prefix, which invalidates the earlier thinking
  blocks on models that check it (the skill's preserved thinking; enforced
  on `claude-opus-5-5` for accounts created from 2026-08-31). A declined or
  cut-off answer, or one without text, stores no turn and cannot be
  followed up (the skill: discard what a refusal streamed). Transition plans
  are never followed up (T14).
